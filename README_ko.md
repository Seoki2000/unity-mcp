AI 에이전트가 Unity 에디터를 **조회하고 제어**할 수 있게 해주는 Unity용 **MCP(Model Context Protocol)** 서버입니다. 이 버전은 로컬 최적화 버전으로, Behavior Tree(행동 트리), 창(Window) 관리, 고급 GameObject/계층(Hierarchy) 조작 기능이 추가로 확장되었습니다.

이 포크(`Seoki2000/unity-mcp`, 브랜치 `optimized`)의 개발 기록. 업스트림과, 게임
프로젝트가 이전에 핀으로 쓰던 `2ea969e` 와 **무엇이 어떻게 다른지 실측값으로** 적는다.
추정이 아니라 살아있는 Unity 에 붙여 JSON-RPC 를 직접 넣고 잰 값이다.

패키지 버전: `2.3.0-dev.0.0.6` · 기준 커밋: `5331a34`

### 구현한 다이어트 — 스펙 기본값 생략 (무손실)

MCP 스펙이 정한 기본값과 같은 힌트는 실어도 정보가 없다. 기본값은
`readOnlyHint=false` / `destructiveHint=`**`true`** / `idempotentHint=false` 다.

`destructiveHint` 가 함정이다. 기본이 true 라서 **false 를 생략하면 안전한 도구가
파괴적으로 뒤집힌다.** 그래서 false 일 때만 명시하고 true 를 생략한다. 대가로 읽는 쪽이
기본값을 적용해야 하는데, 브릿지 자신의 재시도 판단(`isIdempotentTool`)이 그 필드를
그대로 읽고 있었으므로 함께 고쳤다. 서버가 만들 수 있는 8개 조합 전부에서 구/신 판단이
일치함을 확인했다.

실측: **40,376 → 37,067 B (−3,309, −8.2%)**. annotations 5,496 → 2,763 B,
`JsonUtility` 가 남긴 빈 `required:[]` 29개 → 0. 설명과 스키마는 건드리지 않았다.

### 질의당 비용 — 실측

| 질문 | 인덱스 | 대안 |
|---|---|---|
| 이 스크립트가 붙은 에셋은? | 1회 **1,133 B** → 9개 경로 | 프리팹 9개 직접 읽기 **3.8 MB** · GUID grep 2단계 **1,391 B** |
| 이 메서드를 호출하는 곳은? | **412 B** | `grep` **290 B** |

정직하게 적는다. **단순하고 유일한 이름의 호출자 찾기는 grep 이 더 싸다.**
`unity_find_callers` 의 가치는 바이트가 아니라 IL 디코딩 정확성이다 — 주석·문자열 오탐이
없고, 오버로드가 한 키로 병합된다는 사실을 응답에 명시한다.

### 정정 — 응답 상한 30은 구버전에도 있었다

`MAX_RESULTS = 30` 은 `2ea969e` 에도 있었다. **응답이 작아진 것이 아니다.** 달라진 것은
`nextOffset`/`truncated` 로 **상한 너머에 도달할 수 있게** 된 점이다. 구버전은 30개에서
막히고 나머지(예: 에셋 3,142개 중 3,112개)에 접근할 방법이 없었다.

### dev-0.0.1 에서 잡은 인덱스 커버리지 버그

Windows 정션은 `readdirSync` 의 `Dirent` 에서 `isDirectory()` 거짓 / `isSymbolicLink()` 참으로
보고된다. 스캐너는 `isDirectory()` 와 `isFile()` 두 분기만 보고 있었으므로 정션 항목은
어느 쪽에도 걸리지 않고 **통째로 사라졌다.** Unity 는 정션을 따라가므로 그 안의 에셋은
엄연히 프로젝트의 일부인데 인덱스에만 없었다.

이 프로젝트는 `Assets/50.Art` 가 외부 폴더를 가리키는 정션이고, 그 아래 `.meta` 1,105개와
YAML 348개가 빠져 있었다 — 프로젝트 `.meta` 의 **35%**. 게다가 `filesFailed: 0` 이 계속
떠서 빠진 것을 알 방법이 없었다.

| 인덱스 (Assets 기준) | 수정 전 | 수정 후 |

| YAML | 783 | 1,131 |

수정 후 값은 `find`·PowerShell·독립 스캔 세 가지와 교차 확인했다. 결과 정확도도 함께 바뀐다:

### dev-0.0.2 — 직렬화 값 읽기

`unity_get_asset_components` 하나가 추가됐다. 프리팹/씬/에셋의 컴포넌트를 **값까지** 읽고,
`m_Script` GUID 를 지금 컴파일되는 타입 이름으로, 오브젝트 참조를 에셋 경로로 바꿔 준다.

이건 어느 한쪽만으로는 답이 안 나오는 질문이다. `.cs` 를 읽어서는 값을 알 수 없고(값은
에셋 안에 있다), YAML 만 읽어서는 타입을 알 수 없다(에셋에는 GUID 만 있다). 둘을 이어야 나온다.

직렬화된 키는 컴파일된 타입의 필드와 대조한다. 이름이 바뀐 필드가 남긴 낡은 키가 그대로 보인다 —
실측: 필드 검사가 가능한 컴포넌트 864개 중 19개에 그런 키가 있었다(`isGroggyAttack` 등,
값이 있지만 어떤 코드도 읽지 않는다). 베이스 체인이 패키지 어셈블리로 나가 끊기는 242개는
판단하지 않고 그렇게 말한다.

| 실측 (MainProject) | 값 |
|---|---|
| 파서 커버리지 | 텍스트 에셋 1,144개 / 181 MB / 문서 69,891개 → **못 읽은 줄 0** |
| 대조군 | 정규식 스캐너가 찾은 GUID 참조 6,021건 전부가 파싱 트리에도 있다(누락 0) |
| 질의 비용 | 일반 프리팹 **3~4 ms**, 최대 파일(17 MB / 문서 25,449개) **0.7 s** |
| 스크립트 컴포넌트 | **7,019개** — 타입 해석 864 / 패키지라 미해석 5,554 / 없는 스크립트 601 |
| 스윕 | 에셋 1,144개 전수 호출 6.9 s, 오류 4건(전부 바이너리 에셋·32 MB 초과로 정상 보고) |

인덱스에는 넣지 않는다. 값은 **질의 시점에 그 파일 하나만** 파싱한다. 전 프로젝트를 값까지
인덱싱하면 비용이 자릿수로 뛰는데, 대부분의 값은 아무도 묻지 않는다.

파서를 만들면서 Unity 에미터가 줄을 접는 세 형태를 처리해야 했다 — 줄바꿈된 플로우 맵,
접힌 평문 스칼라(어셈블리 수식 이름), 여러 줄 인용 스칼라(TMP 텍스트). 처리 전에는
**못 읽은 줄이 8,456개**였고, 따옴표가 안 닫힌 채 넘어가면서 뒤따르는 형제 키까지 무너졌다.

### dev-0.0.2 에서 고친 정확도 결함 3건

**(1) `guid:` 형태가 아닌 참조를 못 봤다.** VFX Graph 는 오브젝트 참조를 **YAML 문자열 안의
JSON** 으로 쓴다(`m_SerializableObject: '{"obj":{"fileID":…,"guid":"…"}}'`). TMP 폰트 에셋은
원본 폰트를 `m_SourceFontFileGUID: <32hex>` 로, Addressables 는 항목을 `m_GUID: <32hex>` 로
가리킨다. 역참조 인덱스의 정규식은 셋 다 못 봤고, 그 결과 **실제로 참조되는 에셋 3건이
"참조 0" 으로 나왔다** — 그중 하나는 자기 SDF 에셋이 쓰는 `NotoSansKR.ttf` 다.
"안 쓰이니 지워도 된다" 로 읽히는 답이다.

형태를 하나씩 추가하는 방식은 확장자 화이트리스트에서 이미 실패했다. 그래서 형태를 세지 않고
**32자리 hex 토큰 중 실제 `.meta` GUID 인 것**만 참조로 친다. 우연히 일치할 확률은 128비트
난수라 0 이고, 아닌 것(믹서 이펙트 ID, 서명 해시)은 저절로 걸러진다.
비용: YAML 스캔 515 ms → 1.9 s(정규식 두 개를 한 번의 스캔으로 합쳐 2.5 s 에서 줄인 값),
엣지 6,021 → 6,043.

**(2) 본문이 빈 클래스는 타입 해석이 안 됐다.** PDB 의 소스 매핑은 **메서드 본문**에서 나온다.
`public sealed partial class BossStateChanged : EventChannel<TwentyThreeState> { }` 처럼 본문이
없으면 어느 파일에서 왔는지 PDB 가 말해주지 않는다. Assets 안 스크립트 4개가 이 형태였고,
실패 이유는 "컴파일 안 됐거나 어셈블리가 안 빌드됐다" 로 **틀리게** 보고됐다.

파일명 폴백을 넣되 안전장치를 둘 걸었다. 처음엔 "짧은 이름이 유일하면 채택" 만 두었는데
전수 스윕에서 즉시 오답이 나왔다 — URP 패키지의 `Volume.cs` 가 프로젝트 안
`Ami.BroAudio.Volume` 으로 해석됐다. 그래서 (a) 스크립트가 `Assets/` 안일 것,
(b) 후보 타입이 **어떤 소스 파일에도 매핑되지 않을 것** 두 조건을 모두 요구한다.

**(3) 캐시가 지문을 잃고 매 세션 전체 재빌드를 했다.** `unity_find_missing_scripts` 가
PackageCache 를 병합한 뒤 캐시를 다시 저장할 때, 캐시에서 올린 인덱스에는 `fingerprint` 가
복원돼 있지 않아 `null` 이 기록됐다. 다음 세션은 "지문 없는 구 캐시" 로 보고 버렸다.
답은 맞지만 캐시가 조용히 죽는다 — 매번 3.9 s.

여기에 브릿지 쪽 결함 하나가 더 있었다. Unity 가 꺼져 있거나 리로드 중일 때 `tools/list` 를
디스크 캐시로 답하는 경로가 **로컬 도구까지 캐시된 목록 그대로** 냈다. 이번에 추가한
`unity_get_asset_components` 가 목록에서 통째로 빠졌다. 로컬 도구는 Unity 없이 동작하는 것이
존재 이유인데, 하필 Unity 가 없을 때 사라지는 셈이었다. 이제 로컬 도구는 캐시가 아니라
지금 코드에서 다시 만들어 합친다.

### dev-0.0.5 — 영향 분석 (`unity_impact_analysis`)

"이걸 바꾸면 무엇이 깨지나" 를 **축을 합치지 않고** 답한다. 대상은 타입 / `Type::Method` /
에셋(경로·GUID) 셋이고, 축은 아홉이다: IL 호출자 · 파생 타입(상속 폐쇄) · `m_Script` 부착 에셋 ·
참조 에셋 · 인스펙터 배선 · 타입 이름 문자열 · 코드의 경로 상수 로드 · `ProjectSettings`·빌드 씬 ·
속성 진입점.

합계를 만들지 않는 이유: 축마다 고치는 방법이 다르다. 코드 호출자는 컴파일러가 잡아주지만
인스펙터 배선은 조용히 깨지고, 타입 이름 문자열은 이름을 바꾸는 순간 어떤 도구도 안 알려준다.
"영향 12건" 은 어디를 봐야 하는지 말해주지 않는다.

그리고 **`unknown` 이 응답의 일부다.** 동적 로드 44곳 / 인터페이스 구현 목록 없음(타입 53개) /
인덱스 밖으로 나가는 엣지 1,864 / 안 읽은 바이너리 681 / 오버로드 병합 / 중첩 타입 이름 충돌 123 /
디스크 상태 한계. 모든 축이 0 이어도 "안 깨진다" 가 아니다.

전이는 `depth`(기본 1, 최대 3)로 명시한다. 팬아웃 실측(메서드 120 표본):
depth1 중앙 1·p90 3·최대 59 / depth2 중앙 1·p90 5·최대 76. 상속 폐쇄만 완전하다.

비용: `tools/list` +1,237 B(≈+334 토큰/세션), 질의 콜드 1,155 ms / 웜 0~6 ms, 응답 583~2,438 B.

**구현보다 인수 프로브를 먼저 썼다** — `node Tools/probe-impact-analysis.js`, 10개, 첫 실행 10/10.
P1 에서 축 하나가 통째로 빠진 실수를 반복하지 않으려고 순서를 바꾼 것이다.
그런데 프로브가 못 잡은 것이 셋 있었고(없는 대상에 "영향 0" / 모호한 타입 이름을 조용히 해석 /
전이 호출자가 요약에서 누락) 경계 조건을 손으로 훑어서 잡았다. 프로브는 **내가 생각한 질문**만 덮는다.

곁가지로 고친 것 둘:

- **`ProjectSettings` 가 스캔 루트 밖이었다.** 여기 `.asset` 들이 Assets GUID 를 가리킨다.
  그래서 `unity_find_references('0.BootStrapScene.unity')` 가 "참조 1건" 을 답했다 —
  **빌드 0번 씬인데** 빌드 설정이 참조한다는 사실이 빠진 채로. 이제 참조 출처로 읽는다
  (파일 27개, 엣지 6,267 → 6,305).
- **캐시 왕복이 중복 타입 123개를 잃었다.** 캐시로 뜬 세션에서는 모든 짧은 이름이 유일해 보여
  `Segment`·`PassData` 같은 이름이 조용히 하나로 해석됐다. 하루 전 "현재 오답 경로 0건" 으로
  미뤄둔 결함이 두 번째 소비자가 생기면서 실제 오답이 된 것이다.

### dev-0.0.4 — 프로젝트 맵 (`unity_project_map`)

"이 프로젝트가 어떻게 생겼나" 에 예산 안에서 답한다. 로드맵의 원안은 **중심성 랭킹**이었고,
그 전제를 이 프로젝트 데이터로 재보니 **틀렸다.** 게임 레포의 최근 30일 커밋 188건이 건드린
타입을 정답지로 두고(랭킹은 30일 전 데이터로만 — 누수 차단) 채점한 결과:

| 랭킹 | hit@50 | recall@50 |
|---|---|---|
| 균등추출 기준선 | 19.1% | 7.5% |
| 중심성(호출 in-degree) | 28.2% | 12.2% |
| 에셋 부착 수 | 33.0% | 13.6% |
| git churn | 33.5% | 23.0% |
| **부착 → churn** | **35.1%** | 22.1% |

PageRank 상위 20은 컴파일러 생성 타입(`<>c` 는 어셈블리 14개가 한 키로 병합된다),
벤더 오디오 라이브러리, 그리고 `[Conditional("UNITY_EDITOR")]` 로그 래퍼로 채워졌다 —
빌드에는 그 호출이 남지 않는다. 축 간 top20 Jaccard 가 0.03 이라 **합성 점수도 만들지 않는다.**

그래서 주역을 바꿨다. 이 도구가 내는 것은 **코드를 읽어서는 알 수 없는 것**이다:

- `placement.buildScenes` — 빌드 설정의 씬 순서와 enabled. **활성 ≠ 프로덕션**(활성 목록에 dev/test 씬이 섞여 있다)
- `placement.registries` — out-degree 상위 `.asset`(카탈로그·레지스트리). 이름이 아니라 데이터로 찾는다
- `placement.scenes` / `.prefabs` — 씬 21개·프리팹 145개에 실제로 붙어 있는 타입
- `dataOnly` — 코드가 아무도 부르지 않는데 에셋에 붙는 타입 **69개**
- `entryPoints` — 속성(MenuItem 70·Test 59·ClientRpc 39) / 인스펙터 배선 22 / 타입이름 참조 48 / `[Conditional]` 2
- `areas` — 폴더 행, **조인 밀도**(부착 에셋/타입) 정렬. 타입 수로 정렬하면 안 쓰이는 라이브러리가 위로 온다
- `ranked` — 부착→churn 순, 성분(`callerFiles`/`callerTypes`/`assets`/`commits`) 동봉
- `note` — 실측 회수율. 상위 50 이 커밋이 건드린 타입의 22% 만 덮는다는 사실을 응답에 싣는다

비용: `tools/list` +1,236 B(≈+334 토큰/세션), 질의 콜드 1,093 ms(git 250 ms 포함) / 웜 48 ms.
예산 오차 −2.0%~−0.2%.

인수 시험이 리포에 있다 — `node Tools/probe-project-map.js`. 디스크에서 독립적으로 답을 아는
질문 7개를 페이로드에 돌린다: 4,000 → 5/7, **6,000(기본) → 6/7**, 8,000 → 7/7.
첫 구현에서 **타입이름 축이 지도에 통째로 빠져 있던 것을 이 프로브가 잡았다**(리뷰는 두 번 놓쳤다).

### dev-0.0.3 — 데이터가 코드를 부르는 축 (레이어 D)

여기까지의 인덱스는 **코드↔코드**(IL 호출 그래프)와 **데이터↔데이터**(GUID 참조)만 봤다.
Unity 에서는 호출의 상당 부분이 **에셋 안에 데이터로** 들어 있는데 그 축이 통째로 비어 있었고,
그래서 살아있는 코드를 죽었다고 답했다. 실측 재현 두 건:

```
unity_find_callers GameManager::GoToResultButton  → 호출자 0
   실제로는 씬 2개의 버튼에 UnityEvent 로 배선돼 있다. 소스 주석에도 적혀 있다.

BombAction (보스 행동트리 노드)
   get_type_symbols 붙은 에셋 0 / find_callers 0 / find_references 0
   실제로는 Wells.asset 에 "BombAction, Assembly-CSharp, Version=..." 로 들어 있다.
```

둘 다 **"지워도 된다" 로 읽힌다.** 참조 인덱스가 "참조 0" 을 잘못 답하던 것과 같은 형태다.
네 축을 메웠다.

| 축 | 실측 | 어디에 실리나 |
|---|---|---|
| UnityEvent 퍼시스턴트 콜 | 파일 23 / 배선 **24**건, 22건은 조인으로 타입까지 해석 | `find_callers` → `inspectorWirings` |
| 타입 이름 문자열 참조 | 후보 7,460건 중 사용자 타입 **48**개 / 엣지 52 | `find_references`·`find_component_usages`·`get_type_symbols` → `referencedByTypeName` |
| 속성 진입점 | 속성 붙은 메서드 **243**개 (MenuItem 70 / Test 59 / ClientRpc 39 / …) | `find_callers` → `attributes` |
| 경로 기반 로드 | 엣지 **23**개 (해석 25 / 미해석 2 / 여전히 동적 44) | 참조 인덱스에 합류 |

**새 도구는 0개다.** 기존 도구의 응답이 정확해졌을 뿐이라 `tools/list` 고정비는
39,669 B 그대로다. 도구를 늘리는 것보다 이쪽이 낫다 — AI 가 새로 배울 것이 없다.

단, 이 방식에는 조건이 붙는다(2026-08-25 에 배웠다). 타입 이름 축을 처음 붙일 때
`find_component_usages` 와 `get_type_symbols` 에만 실었고 **`find_references` 를 빼먹었다.**
그래서 `unity_find_references(BombAction.cs)` 가 여전히 "참조 0" 을 답했다 — 인덱스는
엣지를 갖고 있는데 정작 "지워도 되나" 를 묻는 이름의 도구가 몰랐다. 스윕 결과 38건.
같은 날 Unity 를 켜서 대조해보니 `AssetDatabase.GetDependencies` 도 이 축을 모르므로
(에셋 24,233개 전수, 참조 0) **두 출처가 합창하는 오답**이었다. 지금은 셋 다 답한다.
도구를 늘리지 않는 선택은 **0 을 답할 수 있는 도구를 빠짐없이 고칠 때만** 정확도가 된다.

설계에서 지킨 것 셋:

- **코드 호출자와 인스펙터 배선을 합치지 않는다.** 하나는 IL 에서 디코딩한 호출이고
  하나는 에셋에 저장된 배선이라 성격이 다르다. 합쳐서 "호출자 3" 이라고 하면
  어느 쪽을 고쳐야 하는지 알 수 없다
- **어떤 속성이 진입점인지 판정하지 않는다.** 프레임워크마다 다르다. 붙어 있는 속성을
  그대로 내고 판단은 읽는 쪽에 맡긴다. 컴파일러 자동 표식만 잡음으로 뺀다
- **필드 이름 화이트리스트를 쓰지 않는다.** `RuntimeTypeString` 같은 이름을 나열하는 대신
  `타입, 어셈블리, Version=` 이라는 **형태**로 잡고, 그 타입이 심볼 인덱스에 실재할 때만
  엣지로 친다. 확장자 화이트리스트에서 이미 실패한 방식을 반복하지 않는다

한 가지 더 알게 된 것: **"정적 인덱스가 원리적으로 못 본다" 고 적어 둔 축도 다시 재보면
상당 부분은 볼 수 있었다.** 경로 기반 로드가 그랬다. 다만 리터럴만 봐서는 안 됐다 —
로드 호출 71개 중 인라인 리터럴은 1개뿐이고 나머지는 경로를 `const string` 에 두고
이름으로 부른다. 같은 파일의 상수를 접어서 풀자 23개가 살아났다.

비용: 레이어 A 3.9 s(경로 로드 포함) / 레이어 B 0.63 s / 호출그래프 0.08 s /
**배선 0.27 s + 타입이름 0.08 s**. 콜드 5.8 s, 캐시 로드 0.9 s.
배선·타입이름 대상 파일은 레이어 A 가 훑을 때 부분 문자열 검사로 미리 골라 두므로
(1,144개 중 23 + 19개) 추가 I/O 가 거의 없다.

### 독립 감사(Codex CLI)와 그 뒤에 고친 것

위 작업을 끝낸 뒤, 결론을 알려주지 않고 같은 코드를 Codex CLI 에 적대적으로 감사시켰다.
동시에 나도 같은 축으로 다시 뒤졌다. 양쪽이 각각 찾은 것을 전부 직접 재현한 뒤 고쳤다.

**(1) 새 도구가 프로젝트 밖 파일을 읽었다.** `getAssetComponents` 는 호출자가 준 경로를
봉쇄 없이 `path.join(root, asset)` 해서 읽었다. `../../..` 로 프로젝트 밖 `.prefab` 을 만들어
부르니 내용이 그대로 응답에 실렸다. Phase 0-A 에서 C# 쪽에 막아 둔 것을 JS 쪽에 다시
들여온 셈이다(이 파일의 다른 질의는 전부 맵 조회라 파일을 열지 않아 지금까지 필요가 없었다).
`McpPathGuard.cs` 와 같은 정책을 JS 에도 두고 12케이스로 검증했다.
Codex 도 같은 것을 독립적으로 찾아 PoC 파일을 만들었다.

**(2) 확장자 화이트리스트를 결국 버렸다.** Codex 가 `.shadergraph` 가 텍스처를 JSON 안의
GUID 로 참조한다는 것을 짚었다. 직접 재현하니 목록 밖 파일이 담은 참조 83건이 인덱스에
없었고, **그 때문에 에셋 19개가 "참조 0"** 으로 답해지고 있었다(셰이더 서브그래프, 텍스처,
`.asmdef`, `.hlsl`). 확장자를 더 넣는 대응은 이미 두 번 실패했으므로(6종 → 24종 → 또 새 형태)
확장자로 고르지 않고 **내용으로** 고른다 — 앞 512바이트에 NUL 이 없으면 텍스트로 보고 훑는다.
틀리는 방향도 안전하다: 바이너리를 텍스트로 오인하면 비용만 들고, 텍스트를 놓치면 답이 틀린다.

| | 값 |
|---|---|
| 스니핑 | 1,508개 **357 ms** |
| 실제로 읽는 것 | 텍스트 816개 **8.7 MB** (바이너리 692개 945 MB 는 안 읽는다) |
| 놓친 (출처,대상) 쌍 | 83 → **0** |

**(3) `.meta` 도 참조 출처다.** FBX 임포터의 `externalObjects` 가 머티리얼을 물고 있다.
참조 130건 / 대상 41개, **그중 18개가 다른 어디에서도 참조되지 않아** 0 을 답하고 있었다.
지우면 임포트한 모델의 머티리얼 할당이 깨진다. `.meta` 전체는 3.5 MB / 314 ms 라
읽는 비용도 사실상 없었다.

**(4) 자기 자신을 참조로 세고 있었다.** 에셋이 자기 GUID 를 본문에 적어두는 경우가 있다
(BroAudio 의 `_assetGUID`). 맨 GUID 스캔을 넣자 그런 엣지가 4건 생겼고, 아무도 안 쓰는
에셋이 쓰이는 것처럼 보였다.

**(5) 텍스트 일치와 직렬화 참조를 구분한다.** Codex 가 반례 픽스처를 만들었다 —
사용자 문자열 필드에 32자리 hex 를 적어두면 참조 엣지가 생긴다. 실제 GUID 는 난수라
그 픽스처(`aaaa…`)는 인위적이지만, 지적 자체는 맞다: 소스코드·문서에서 나온 엣지와
프리팹의 참조 필드에서 나온 엣지가 응답에서 같아 보이면 삭제 판단이 흐려진다.
이제 전자를 `textualMatches` 로 따로 싣는다(이 프로젝트에서 대상 58개).

**(6) 조용히 잘리던 것들.** 파서 상한(배열 200개)에 걸려 잘린 사실이 응답에 없었다 —
자식 710개인 Transform 이 200 으로 보였다(문서 24개가 해당). ScriptableObject 의
`m_Name` 은 통째로 버려지고 있었다(컴포넌트의 빈 `m_Name` 만 감춰야 하는데 구분을 안 했다).
그리고 이번 전수 집계 자체가 파일당 500개 페이지 상한에 걸려 **컴포넌트 39,921개를 안 보고**
있었다 — 처음 적었던 "5,418개" 는 과소 집계였고, 실제는 **7,019개**다.
Codex 의 독립 집계(7,019 / 864)와 일치한다.

**(7) 캐시 버전을 올려야 했다.** 지문은 디스크 상태만 본다. 엣지 규칙이 바뀐 것은 못 잡는다.
버전을 안 올리면 기존 캐시가 옛 엣지를 계속 서빙하고 고친 오답이 그대로 남는다(5 → 6).

Codex 의 독립 재측정이 내 수치를 확인해 준 것도 있다: Missing Script **14 / 134 / 164**,
`m_EditorClassIdentifier` 불일치 **11건**. 어제 보고서의 13/133/163 이 재현되지 않는다는
내 판단이 맞았다.

| 단계 | 시간 | 내용 |
|---|---|---|
| 레이어 A | 3.3 s | 수집 0.5 / `.meta` 3,142개 0.4 / YAML 1,144파일 181 MB 1.7 / 기타 텍스트 0.5 |
| 레이어 B | 0.55 s | DLL → 사용자 어셈블리 14 / 타입 1,169 / 소스 560 |
| 호출 그래프 | 0.07 s | 메서드 7,170 디코딩, 실패 0, 엣지 8,673 |
| **전체(콜드)** | **3.9 s** | 참조 엣지 **6,244** (맨 GUID 18 / `.meta` 122 / 기타 텍스트 83) |
| 캐시 로드 | 0.75 s | 대부분이 지문 재계산(파일 5,794개 stat) |
| 질의 | 0~1 ms | `unity_find_references` |

dev-0.0.1 표(레이어 A 615 ms)와 비교하면 커 보이지만, 그 표는 **정션 수정 이전** 수치다
(YAML 783파일 115 MB → 1,144파일 181 MB). 늘어난 몫의 대부분은 그때까지 안 보던 35% 이고,
이번에 추가된 몫은 맨 GUID 스캔 약 1.3 s 다.

### 알려진 한계

- **인덱스 증분 갱신 미구현.** 변경 파일만 다시 읽지는 않는다 — 낡음을 감지하면 **전체를 다시 만든다**
  (콜드 4.8 s). 다만 dev-0.0.6 부터는 `ensureIndex` 가 호출마다 신선도를 검증하므로
  `unity_index_rebuild` 를 손으로 부를 필요는 없다: 어셈블리 서명은 매 호출(11~18 ms),
  에셋 지문은 10초 throttle 로 대조한다.
  캐시는 `fromCache: true` 로 표시되지만 무엇이 낡았는지는 알려주지 않는다
- **`assetGuidPairCount` 는 (에셋, GUID) 쌍을 센다.** 원시 등장 횟수가 아니다. 실측 예:
  같은 GUID 가 원시 515회 등장하지만 108개 에셋에 걸쳐 있으면 108로 보고된다.
  행 단위 `referencingAssetCount` 도 등장 횟수가 아니라 **서로 다른 에셋 수**다.
  dev-0.0.7 에서 `totalReferenceCount`/`referenceCount` 에서 이름을 바꿨다 — 옛 이름은
  값이 담지 않는 것을 주장하고 있었다. 같은 응답의 `affectedAssetCount`(전역 중복 제거,
  실측 134)와 `assetGuidPairCount`(실측 164)는 **다른 값이다**
- **`unity_find_callers` 는 프로젝트 어셈블리 내부 호출만** 인덱스한다. UnityEngine/BCL 로
  들어가는 호출은 제외되고, 오버로드는 `Type::Method` 한 키로 병합된다
- **`tools/list` 고정비가 여전히 `2ea969e` 보다 크다.** 다이어트로 −8.2% 를 되돌렸지만
  순증가는 남아 있다. 도구를 더 줄이려면 기능을 포기해야 한다
- **컴포넌트 값은 질의마다 다시 파싱한다.** 캐시하지 않는다. 일반 프리팹은 3~4 ms 지만
  17 MB 프리팹을 페이지로 훑으면 매 호출 0.7 s 를 다시 쓴다
- **패키지 스크립트는 심볼이 없다.** 인덱스는 사용자 어셈블리만 담으므로 PackageCache 안의
  MonoBehaviour 는 타입이 `null` 로 나온다. 컴포넌트가 없다는 뜻이 아니라 이름을 모른다는 뜻이다
- **참조가 GUID 로 저장되지 않으면 어떤 정적 인덱스도 못 본다.** `Resources.Load("path")`,
  Addressables 주소 문자열, 런타임에 조립하는 경로가 그렇다. 이제 텍스트 파일은 전부 훑지만
  이 축은 원리적으로 남는다 — 0 응답에 그렇게 적는다
- **부분 커버리지에서는 `script.exists` 가 `null` 이다.** `Assets`/`Packages` 만 인덱싱한
  상태에서 PackageCache 스크립트를 `false`(없음)로 단정하면 실측 기준 4,667건이 "없는
  스크립트" 로 잡힌다. 실제는 270건이다 — 모를 때는 `null` 을 낸다
- **런처는 고정 경로에서 실행돼야 한다.** git URL 핀으로 소비하면 런처가 `PackageCache`
  안에 놓여 경로가 핀마다 바뀐다. `LOCAL_DEV_SETUP.md` 참조

### 실측 재현 방법

브릿지에 JSON-RPC 를 직접 넣으면 위 숫자를 다시 잴 수 있다. Unity 에디터가 켜져 있어야 한다.

```bash
cd <UnityProject>
node <package>/Bridge/mcp-bridge-launcher.js <<'EOF'
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"unity_index_status","arguments":{}}}
EOF
```

`id=2` 응답의 바이트 수가 세션 고정비다. `id=3` 은 인덱스 커버리지(`metaFiles`/`yamlFiles`)를
보여준다 — 프로젝트의 실제 파일 수와 어긋나면 정션이나 낡은 캐시를 의심한다.

## MCP란?
MCP는 AI 시스템이 외부 도구와 데이터에 접근할 수 있도록 앤스로픽(Anthropic)이 만든 개방형 표준입니다. 이 패키지를 사용하면 Unity를 MCP 서버로 변환하여 **Antigravity**, **Claude**, **Cursor**와 같은 AI 어시스턴트가 씬을 조회하고, 에셋을 수정하며, 에디터 명령을 실행할 수 있게 됩니다.

## 주요 기능
- 🎮 **씬 & 계층 제어**: GameObject 생성/수정, 부모 설정, 특정 컴포넌트를 가진 오브젝트 찾기.
- 🧩 **컴포넌트 관리**: 컴포넌트 추가/제거 및 직렬화된 속성(Property) 깊은 탐색.
- 🌲 **Behavior Tree 도구 (신규)**: Unity Behavior 그래프 관리 (노드 추가/삭제/연결, 속성 설정).
- 🪟 **창 관리 (신규)**: Animator 또는 Behavior 그래프와 같은 에디터 창 열기.
- 🎬 **씬 & 프리팹 관리**: 씬 열기/저장, 프리팹 생성 및 해제.
- 📦 **에셋 & 리소스 접근**: 프로젝트 에셋 탐색, 이동, 복제, 읽기.
- ▶️ **플레이 모드 & 입력**: 플레이 모드 상태 제어 및 키보드/마우스 입력 시뮬레이션.

## 설치 방법 (Git URL 방식)
1. Unity에서 `Window > Package Manager`를 엽니다.
2. 좌측 상단의 `+` 아이콘을 클릭하고 `Add package from git URL...`을 선택합니다.
3. 아래의 저장소 URL을 입력합니다 (또는 로컬 클론 경로 사용):
   ```text
   https://github.com/Seoki2000/unity-mcp.git#optimized
   ```

   이 패키지는 [usmanbutt-dev/unity-mcp](https://github.com/usmanbutt-dev/unity-mcp) 의 포크입니다.
   `optimized` 가 이 포크의 정본 브랜치입니다 — 무엇이 다른지는 위 [dev-0.0.1](#포크-개발-버전--dev-001) 참조.
   이 패키지를 쓰는 프로젝트는 브랜치 이름이 아니라 **커밋 SHA 로 핀** 하는 것을 권합니다.

## 빠른 시작
1. Unity 프로젝트를 로드하면 서버가 **자동으로 시작**됩니다.
2. `Window > MCP Server`로 이동하여 서버 상태를 확인합니다.
3. **"Copy Config to Clipboard"** 버튼을 클릭합니다.
4. 복사한 설정값을 사용 중인 MCP 클라이언트의 설정 파일(예: `mcp_config.json`)에 붙여넣습니다.

## 사용 가능한 도구 (도구 확장됨)

### 🧩 GameObject & 컴포넌트 도구
| 도구 이름 | 설명 |
|------|-------------|
| `unity_create_gameobject` | 새로운 GameObject 생성 (기본 도형 지원). |
| `unity_delete_gameobject` | 씬에서 GameObject 삭제. |
| `unity_set_transform` | 위치(Position), 회전(Rotation), 크기(Scale) 수정. |
| `unity_add_component` | GameObject에 컴포넌트 추가. |
| `unity_remove_component` | GameObject에서 컴포넌트 제거. |
| `unity_set_component_property` | 특정 컴포넌트 속성 값 설정. |
| `unity_get_component_properties` | **[신규]** 컴포넌트의 모든 직렬화된 속성(Property)과 값을 가져옵니다. |

### 🌲 계층(Hierarchy) 도구
| 도구 이름 | 설명 |
|------|-------------|
| `unity_get_hierarchy` | 현재 씬의 GameObject 계층 구조를 가져옵니다. |
| `unity_get_gameobject` | 특정 GameObject의 세부 정보를 가져옵니다. |
| `unity_get_components` | GameObject에 부착된 컴포넌트 목록을 가져옵니다. |
| `unity_find_objects_by_component`| **[신규]** 활성 씬에서 특정 컴포넌트를 가진 모든 GameObject를 찾습니다. |
| `unity_set_object_parent` | **[신규]** GameObject의 부모를 다른 GameObject로 변경(Reparent)합니다. |

### 🧠 Behavior Tree 도구 (신규)
| 도구 이름 | 설명 |
|------|-------------|
| `unity_get_bt_graph` | Behavior 그래프의 세부 정보(노드, 엣지, 블랙보드)를 가져옵니다. |
| `unity_add_bt_node` | Behavior 그래프에 새 노드를 추가합니다. |
| `unity_remove_bt_node` | Behavior 그래프에서 노드를 제거합니다. |
| `unity_connect_bt_nodes` | Behavior 그래프 안의 두 노드를 연결합니다. |
| `unity_set_bt_node_property`| Behavior 그래프 노드의 속성 값을 설정합니다. |

### 🪟 창(Window) 관리 도구 (신규)
| 도구 이름 | 설명 |
|------|-------------|
| `unity_open_animator_window`| Unity 에디터에서 Animator 창을 엽니다. |
| `unity_open_bt_window` | Unity Behavior (BT) 창을 엽니다. |

### 🏃 애니메이션 도구

|------|-------------|
